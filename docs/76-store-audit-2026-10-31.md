## 4. Two real bugs this audit found

**(a) `tools/setup.mjs` could not install on Windows.** It called `execFileSync('npm', ...)`, which
fails with `ENOENT`, then `npm.cmd`, which fails with `EINVAL` (Node refuses to spawn a `.cmd` without a
shell). Both errors were reproduced here. Fixed by probing and running through a shell on win32.

**(b) The plugin declared no UI position.** `preflight` flagged `ui-placement`: "renders into 1 UI
surface(s) but declares no slot/anchor/order". Two plugins with hardcoded positions fight over the same
corner, which is exactly what the store's placement rule is about. The plugin's own patch row now
declares:

```yaml
slot: shell.overlay
anchor: bottom-right
order: 900
```

After reinstalling, `ui-placement` reports **no findings** and the whole gate reads `clear to install`.

## 6. The five model modules must load on the real profile (found by checking, not assuming)

After syncing the plugin into the running profile and restarting the harness, four of five module
routes answered and two did not:

```
capabilities.js 200   selection.js 200   history-timeline.js 200
field-schema.js 404   hooks.js 404
```

Cause: the host routes existed only in `tools/console-server.mjs` (the test server). The real plugin's
`lib/index.js` still registered one block per module, and the two newest modules had never been added.
The fixtures could not catch this because the fixture server serves the page, not the plugin.

Fix: one loop over a `MODULES` list replaces five copied blocks, so a new module is one list entry.
After a restart, all five answer 200 and the live console reports:

```
capabilities/selection/history/fields/hooks: object
designer timeline panel: 1
pageerrors: 0
```

This is the third time in this project that "the repo is not the running system" cost a round
(docs/67, docs/68, and here). The difference this time: `sync-live.mjs` reported `in sync (20 files)`,
which is what made the missing routes the obvious suspect instead of a mystery.
