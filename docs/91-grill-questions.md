## 决策 1：这套东西的**用户**是谁？

**事实**：今天暴露了三类用户——新手（照教程装）、你（主 DSH 重度使用）、我（mini 实验场）。
体检面板目前按「当前 profile」报告，新手看不懂 profile 是什么。

**推荐答案**：主用户 = **你**（这台机器、这个主 profile）。新手场景只保留 `docs/faq/` 文档，不做成 UI。
理由：把新手引导做成 UI 会再次膨胀；文档 + `setup-check` 已够。

## 决策 2：`diagnose.mjs` 的**触发时机**？

**推荐答案**：三种都要，但按成本排序——① 手动（随时可跑）② 面板「开始体检」③ **DSH 启动失败时自动跑一次**（抓崩溃前的状态）。
第三条最关键：今天 AA 挂掉时没有任何自动证据留存。

## 决策 3：出站探测**测什么**（决定误报率）？

**事实**：刚才实测 `直连 baidu 200 / 7897 google 000 / 7897 deepseek 401 / 31181 github 000`。

**推荐答案**：固定四个目标 + 三条路径（直连、7897、31181），共 12 个探测，每个记 `{target, path, code, ms}`：

| 目标 | 为什么 |
|---|---|
| `web.agents-anywhere.com` | 今天的真实故障点 |
| `api.deepseek.com` | 模型链路 |
| `github.com` | 插件安装 / git 依赖 |
| `registry.npmjs.org` | 插件安装 |

**不做**：不做 DNS 劫持检测、不做带宽测速（成本高、结论弱）。

## 决策 4：诊断结论的**格式**？

**推荐答案**：固定三段——`现象` / `证据`（原始行 + 文件路径 + 时间）/ `修法`（一条可复制命令）。
禁止输出「可能」「建议检查」这种无动作句子。

## 决策 5：环境管家面板要不要**真的执行动作**（重启 mini / 修复）？

**事实**：你已明确「不管商店，功能优先」，所以 `child_process` 可以用。

**推荐答案**：**只做两类动作**，且都必须二次确认 + 有回滚：

1. 重启 mini（`scripts/start-mini.ps1` 已存在）
2. 生成修复方案并展示，由你点「执行」——执行走已有的 txn（计划/确认/前置哈希/回滚）

**不做**：自动改代理、自动改第三方插件、自动装/卸插件（这三类风险高、收益低）。

## 决策 6：mini 到底承担什么角色？

**今天的事实**：mini 对 AA 问题零贡献，因为 AA 桥写全局路径、要真实桌面进程，mini 复现不了。

**推荐答案**：mini 明确为「**插件与 UI 的沙盒**」——凡是 `~/.dsh/profiles/*` 内的写入、插件装配、UI 注入都先在 mini 验；
凡是「涉及全局路径 / 外部进程 / 网络」的，mini 直接标注 `cannot-reproduce`，转而在主 profile 上做只读诊断。
这条要写进 SDS，避免以后又期待 mini 兜底一切。

## 决策 7：今天的坑，哪些进回归、哪些只进文档？

**推荐答案**：

| 坑 | 处理 |
|---|---|
| 代理掐断出站 | 进回归（夹具模拟 ConnectError） |
| 插件/桌面端版本不匹配 | 进回归（版本矩阵） |
| 双市场冲突 | 进回归（装前现状检查） |
| `client bundle` 加载失败（`Unexpected token '}'`） | 进回归（按 DSH 注入方式解析） |
| sidebar 按钮排版 | **只进文档**（属个人审美，不做夹具） |
| md/图片渲染异常 | 只进文档（未确认根因，不编造） |

## 决策 8：什么时候算「完成」？

**推荐答案**：以下三条同时成立——

1. 拿今天三个故障的**真实日志**回放，`diagnose.mjs` 能各自给出正确结论（不只是「有输出」）
2. 面板里能看到同样的结论，且每条给得出可复制命令
3. 五个坑各有夹具，`npm test` 一次跑完全绿
