## 一、重新定义失败模式

| v1 的说法 | 实际 |
|---|---|
| 缺一个能测出站的工具 | 今天我测过，但**测法不对**：curl 没带 CA → 000 → 判成环境坏 |
| 缺版本矩阵 | 三者都 2.1.0 之后仍然坏，坏的是**第四方 codex-cli** |
| 缺日志解析 | 日志我读了，但**手动读的是嵌套 record，写规则时会读不出来** |

**统一失败模式：我把「一个合理假设」当成结论，并且没有规定「什么证据能推翻它」。**

## 二、diagnose 的原则（v2 的核心）

```
1. 先定位受害进程（谁在报错），不是先枚举网络
2. 读该进程真实使用的路径：它的 env、它加载的插件配置、它声明的服务地址
3. 一次只排除一层：DNS → TCP → TLS → HTTP 状态 → 应用层响应体
4. 「成功」= 拿到了真实应用响应（如 422/401 也算通），不是 TCP connected
5. 每条结论必须附「什么结果能推翻它」
6. 允许输出「判不出」，并说明缺哪条证据
```

## 三、分阶段（删掉了评审否掉的两阶段）

| 阶段 | 内容 | 验收（对真实数据，不对自写夹具） |
|---|---|---|
| P1 | 日志格式统计器：对 `~/.agents-anywhere/logs/runtime-*.jsonl` 输出顶层键分布、level 分布、错误串 TopN | 在今天这份 395KB 日志上跑出 `unknown variant` 计数 222、目录结构识别正确 |
| P2 | 受害进程定位：给定错误串，回溯出是哪个 runtime（dsh / codex / claude） | 对今天日志输出 `codex`，且不把 dsh 判成故障 |
| P3 | 分层探测（只针对该进程的真实路径） | 对 AA 直连路径输出「422 = 通」而不是布尔 |
| P4 | 结论与修法（含推翻条件） | 今天两条判定都能复现：DSH 通 / Codex 协议不兼容 |
| P5 | 面板接入（复用 `/turnstile/health`，不新建链路） | 面板显示同一份结论 |

**删除**：12 格矩阵、崩溃钩子、重启 mini、把「装前检查」做成独立阶段（改为焊进安装命令）。

## 四、验收的硬标准（替代「夹具全绿」）

```
对 2026-10-31 的三段真实证据回放：
  A. AA runtime 日志（含 222 条 unknown variant）
  B. 我那条假阳性的 curl（无 CA → 000）
  C. pnpm 因 git 依赖失败的输出
diagnose 必须分别给出：
  A. 判出 codex-cli 协议不兼容，且不说 DSH 有问题
  B. 判出「这是探测方法错误（缺 CA）」，不是环境故障
  C. 判出「不可解析依赖 → 手工装法」并给出本地化修法
任一判错 → 阶段未完成。
```

## 五、mini 的新定位（替代 cannot-reproduce 标签）

不再打「测不了」的二元标签，而是写清两件事：

| 维度 | 内容 |
|---|---|
| mini **能验什么** | profile 内写入、插件装配、UI 注入、控制台行为 |
| 复现还缺什么条件 | 缺全局路径写入 / 缺外部进程 / 缺真实网络 —— 逐项列出 |

这样「mini 没帮上忙」会变成一条明确的缺口清单，而不是一句免责声明。
